# Хроника — исторический атлас

Vue 3 + TypeScript + Vuetify → FastAPI → PostgreSQL 17. Персоны, биографии,
классификация и направленные связи сохраняются в базе. Браузер получает данные
через `/api`; локальный массив больше не используется как хранилище.

Страна в переключателе «Смотрим со стороны» задаёт точку зрения всего атласа:
обзора, шкалы, коллекции, карты и генеалогии. Выбирается одна страна; выбор
сохраняется при переходе между страницами и после перезагрузки. По умолчанию
выбирается «Русь / Россия», если она есть, иначе первая доступная страна.

В карточке страна и группа задают основную роль. В разделе «Роли в других
странах» можно добавить независимые назначения: например, Витовт — правитель
Литвы и современник для Руси / России. Допускается роль правителя нескольких
стран. Иностранное происхождение само по себе не создаёт роль современника:
для включения персоны в другую точку зрения назначьте её явно. Без назначения
персона в этой стране не показывается. Полная карточка и редактор сохраняют
все связи, включая связи с персонами вне текущей точки зрения.

## Статическая версия для GitHub Pages

Вариант для публикации коллекции без сервера и базы: просмотр карточек, шкалы,
связей и генеалогии, поиск и JSON-экспорт. Вход и изменение данных недоступны.
Данные читаются из `frontend/public/data/people.json`; сайт не обращается к API.
Это публичная копия коллекции на момент выгрузки, обновления локальной БД
появятся на сайте после новой выгрузки, сборки и публикации.

Выгрузите текущую коллекцию из работающего приложения:

```powershell
cd frontend
npm run snapshot:export
npm run build:static
npm run preview:static
```

Предпросмотр: http://localhost:4173. Сборка находится в `frontend/dist-static`.
Для разработки статической версии: `npm run dev:static` (порт 3001).
Обычный `npm run build` по-прежнему собирает приложение с API в `frontend/dist`.

Для другого адреса приложения: `npm run snapshot:export -- http://localhost:8000`.
Также можно загрузить JSON, полученный кнопкой экспорта:
`npm run snapshot:export -- C:/Downloads/chronicle.json`.
Проверка формата выполняется до замены файла; неудачная выгрузка сохраняет
предыдущую копию. В снимок входят только данные персон из публичного API,
учётные записи и сессии не выгружаются.

Публикация на GitHub Pages:

1. Загрузите проект в GitHub-репозиторий вместе с `frontend/public/data/people.json`
   и `.github/workflows/pages.yml`. Не добавляйте `.env` и файл пароля редактора.
2. В репозитории выберите **Settings → Pages → Source → GitHub Actions**.
3. В **Actions → Publish static atlas → Run workflow** запустите публикацию.
4. После завершения адрес будет показан в окружении `github-pages`.

Workflow запускается вручную. Чтобы обновить опубликованную коллекцию,
выгрузите новый JSON, отправьте его в репозиторий и снова запустите workflow.
Относительные пути позволяют разместить сборку и на корневом домене, и по
адресу вида `https://USER.github.io/REPOSITORY/`. Навигация использует `#/…`,
поэтому обновление страницы не требует настройки серверных маршрутов.

## Запуск с базой данных

Нужен запущенный Docker Desktop с Linux containers. Из корня проекта:

```powershell
Copy-Item .env.example .env
docker compose up -d --build
```

- Приложение: http://localhost:3000
- Swagger / OpenAPI: http://localhost:8000/docs
- Проверка API и соединения с БД: http://localhost:8000/api/health
- PostgreSQL: `127.0.0.1:5432`, база/пользователь/пароль по умолчанию — `chronicle`.

Порты и реквизиты задаются в корневом `.env`. При изменении пароля учитывайте,
что пароль в URL подключения требует percent-encoding для специальных символов.
Пример рассчитан на локальную личную коллекцию: сервисы опубликованы только на
loopback. Без входа доступен только просмотр; изменять коллекцию могут редакторы.

## Доступ редактора

Посетитель без входа может просматривать все разделы и карточки персон, искать,
фильтровать и выгружать JSON. Добавление, изменение, удаление и импорт защищены
на сервере. В интерфейсе кнопки изменения доступны после входа редактора.

После первого запуска создайте редактора (регистрации через сайт нет):

```powershell
docker compose exec backend python -m app.manage_editor editor
```

Команда дважды запросит пароль без отображения ввода (от 12 до 1024 символов).
Логин приводится к нижнему регистру. Нажмите «Войти как редактор» в приложении.
Для локального backend используйте `uv run python -m app.manage_editor editor`
из каталога `backend`, после применения миграций.

Повторный запуск команды меняет пароль, включает учётную запись и отзывает все
её сессии. Для отключения редактора:

```powershell
docker compose exec backend python -m app.manage_editor editor --disable
```

Миграция `0003` добавляет таблицы `editors` и `editor_sessions`, сохраняя прежние
персоны и связи. В БД хранятся только хеши паролей PBKDF2-SHA256 с индивидуальной
солью и 600 000 итераций, а также SHA-256 хеши случайных токенов сессий.
Пароль по умолчанию отсутствует. После пяти неверных попыток входа учётная запись
блокируется на пять минут. Доступ проверяется по БД при каждом изменении.

Сессия хранится в HttpOnly cookie с SameSite=Lax и действует `SESSION_HOURS`
часов (по умолчанию 12). Выход удаляет сессию из БД. Изменяющие запросы, вход
и выход требуют заголовок `X-Requested-With: Chronicle` для защиты от CSRF.
Для HTTPS задайте `COOKIE_SECURE=true`; при другом адресе интерфейса укажите
его полный origin в `CORS_ORIGINS`. Интерфейс и API рекомендуется обслуживать
с одного origin через имеющийся прокси `/api`.

Настройки передаются через корневой `.env` в Docker Compose; для локального
backend используются те же переменные в `backend/.env`. После изменения
настроек Compose выполните `docker compose up -d --build`.

Backend при запуске применяет миграции Alembic. Первая миграция создаёт таблицы
и девять исходных персон; последующие запуски не восстанавливают удалённые записи
и не перезаписывают изменения. PostgreSQL хранит данные в named volume
`postgres_data`, который сохраняется после `docker compose down`.
Команда `docker compose down -v` удаляет и этот том с данными.

Логи: `docker compose logs -f backend`. Остановка: `docker compose down`.

## Перенос прежней коллекции

Откройте приложение в том же браузере и на том же адресе, где пользовались им
раньше. Если обнаружен ключ `chronicle-v1`, появится кнопка «Перенести в базу».
Она переносит записи и связи одной транзакцией: совпавшие ID обновляются,
остальные записи в базе сохраняются. При ошибке откатывается весь перенос.
Старый одиночный `relation` преобразуется фронтом в `relations`.

Копия в localStorage остаётся без изменений. После успешного переноса браузер
запоминает его завершение. Для другого порта, hostname или браузера старый
localStorage недоступен. JSON-экспорт текущей коллекции продолжает работать.

## Разработка

База в Docker, backend и Vite локально. Python 3.12+, uv, Node.js 22.12+ и npm.
Если весь стек уже запущен, сначала освободите порты backend/frontend:

```powershell
docker compose stop frontend backend
docker compose up -d db
```

В отдельном терминале:

```powershell
cd backend
Copy-Item .env.example .env
uv sync --frozen
uv run alembic upgrade head
uv run uvicorn app.main:app --reload --host 127.0.0.1 --port 8000
```

В другом терминале:

```powershell
cd frontend
npm ci
npm run dev
```

Vite проксирует `/api` на `127.0.0.1:8000`. В Docker это делает nginx.
При необходимости задайте `API_PROXY_TARGET` в `frontend/.env` для Vite
или `VITE_API_BASE_URL` для отдельного адреса API (подставляется при сборке).
Для прямого обращения к API с другого origin добавьте его в `CORS_ORIGINS`
backend: переменная принимает JSON-массив строк. Backend читает `.env` из своей
рабочей директории; корневой `.env` предназначен для Compose.

## Данные и API

`people` хранит ФИО, годы жизни, группу, страну, регион, династию, заметку,
биографию, источники, признак «до указанного года» и время создания/обновления.
Источники указываются отдельной необязательной строкой: книги, статьи или ссылки
до 5000 символов. Поле сохраняется в БД и JSON-экспорте; в карточке просмотра
отображается под биографией. Миграция `0004` добавляет пустое поле прежним записям.
`person_relations` хранит направленные связи через два внешних ключа на персон.
При удалении персоны её входящие и исходящие связи удаляются каскадно.
Дубли роли у той же пары, связи с собой и неверные годы ограничены также в БД.

Схема запросов остаётся совместимой с camelCase фронта (`firstName`, `personId`).
Поле `name` собирается сервером из ФИО, когда указан `firstName`; старые записи
с одним `name` поддерживаются без автоматического разбора исторических имён.

| Метод | Адрес | Действие |
| --- | --- | --- |
| GET | `/api/people` | Вся коллекция |
| POST | `/api/people` | Создание, ID генерирует сервер |
| GET | `/api/people/{id}` | Одна персона |
| PUT | `/api/people/{id}` | Полная замена полей и исходящих связей |
| DELETE | `/api/people/{id}` | Удаление персоны и связей |
| POST | `/api/people/import` | Атомарный импорт `{ "people": [...] }` с ID |
| GET | `/api/health` | Проверка соединения с БД |
| GET | `/api/auth/me` | Текущий редактор или режим просмотра |
| POST | `/api/auth/login` | Вход: `{ "username": "editor", "password": "..." }` |
| POST | `/api/auth/logout` | Выход и отзыв сессии |

Все POST/PUT/DELETE для `/api/people` требуют сессии редактора и защитного
заголовка. При прямом вызове API передайте cookie, полученную при входе.
Кнопка удаления персоны в интерфейсе пока не добавлена.
При недоступности API интерфейс показывает ошибку и повторную загрузку.
Неудачное сохранение оставляет форму открытой и не изменяет коллекцию на экране.

Изменения схемы:

```powershell
cd backend
uv run alembic revision --autogenerate -m "describe change"
# Проверьте созданную миграцию перед применением.
uv run alembic upgrade head
uv run alembic check
```

Подход к сессиям описан в [FastAPI](https://fastapi.tiangolo.com/tutorial/sql-databases/),
управление схемой — в [Alembic](https://alembic.sqlalchemy.org/en/latest/tutorial.html).

## Проверки

```powershell
cd backend
uv run ruff check app migrations tests main.py
uv run pytest -q
cd ../frontend
npm run lint
npm run build
```

Без `TEST_DATABASE_URL` тесты используют отдельную временную SQLite-базу.
Для проверки именно PostgreSQL из корня создайте отдельную БД:

```powershell
docker compose exec -T db createdb -U chronicle chronicle_test
cd backend
$env:TEST_DATABASE_URL = 'postgresql+psycopg://chronicle:chronicle@127.0.0.1:5432/chronicle_test?connect_timeout=5'
uv run pytest -q
```

Тесты пересоздают таблицы; для PostgreSQL разрешены только имена БД с суффиксом
`_test`. Проверяются CRUD, сохранение связей, каскадное удаление, валидация,
атомарность и повторный импорт, миграции вверх/вниз и соответствие модели схеме.

## Резервная копия PostgreSQL

Для реквизитов по умолчанию, из корня проекта:

```powershell
docker compose exec -T db pg_dump -U chronicle -d chronicle -f /tmp/chronicle.sql
docker compose cp db:/tmp/chronicle.sql ./chronicle.sql
```

SQL-файл храните отдельно от Docker volume. Если меняли реквизиты, подставьте
свои имя пользователя и базы.
